# Паприка

Паприка — это простой и быстрый трекер задач для VFX. Создан для организации командной работы над VFX-проектами. Позволяет распределять задачи, отслеживать прогресс, загружать и отсматривать видео.

Пишется одиноким композером в перерывах между проектами.

## Зачем еще один?

В первую очередь — это инструмент для меня самого, чтобы избавится от Excel-табличек, загрузки дейлизов в облако и поиска информации в бесконечных чатах. Хочу быстро понимать какие задачи взяты в работу, какие кадры готовы, кто и что делает, собрать всю информацию по проекту в одном месте.

## Почему не взять готовое решение?

Есть же Cerebro, Ftrack, Frame.io, Kitsu и прочие. Причин несколько:

- Давняя мечта — много лет хотел создать свою идеальную систему ведения проектов. Но полноценное ведение проектов это сложно, поэтому — трекер задач.
- Мне нравится программировать — а с нейросетями это вообще полнейший улет.
- Хочу создать полезную штуку, которая поможет людям.

## Сколько стоит?

Бесплатно, но ставить надо на свой сервер. Или можно просто локально на компьютер. Установка простая и подробно описана в документации.

## Технический стек

### Бэкенд

- Django + django-modern-rest + JWT
- django-guardian — права доступа на уровне объектов
- django-storages — работа с хранилищем медиа
- Django Channels — обновление интерфейса в реальном времени, чат, уведомления
- Celery + Redis — фоновые задачи (пакетная загрузка, конвертация видео, отправка уведомлений)
- PostgreSQL

### Фронтенд

- Vue.js + Composition API + Pinia

### Инфраструктура

- Контейнеризация: Docker Compose
- Веб- и прокси-сервер: Caddy
- Запуск команд: Just

## Основные сущности

- **Пользователь** — кастомная модель пользователя Django с дополнительными полями. Может быть участником в нескольких компаниях.

- **Компания** — верхний уровень иерархии. Обеспечивает полную изоляцию данных между независимыми организациями на одной установке. Заложена в архитектуру с самого начала для простого расширения в будущем.

- **Команда** — группа пользователей. Используется для разбиения по командам, отделам, правам доступа и т.п.

- **Проект** — принадлежит компании. Содержит все данные проекта: группы кадров, кадры, задачи, версии, участников и прочие.

- **Группа кадров** — произвольная группировка кадров внутри проекта. Используется для разбиения по сериям, приоритету, крупности кадра и т.д.

- **Кадр** — основная производственная единица. Содержит задачи, версии и чат.

- **Задача** — конкретная работа, которую нужно выполнить. Может быть привязана к кадру или существовать самостоятельно на уровне проекта (например, «снять футажи дыма»). Также имеет собственный чат.

- **Статус** — статус задачи или кадра. Используется для отслеживания прогресса работы. Набор статусов можно менять под каждый проект. Есть предустановленный набор.

- **Версия** — результат работы над задачей — видео или картинка. Для каждого кадра или задачи хранится полная история версий.

- **Чат** — содержит всю переписку по работе над кадром или задачей. С упоминаниями (пользователей, кадров, задач), с реакциями и поддержкой Markdown.

Будут нужны дополнительные сущности, например для чата, уведомлений, настроек и прочего. А также вспомогательные сущности, например связь кадр-задача и другие.

Продумать систему _типов_ загружаемых файлов. Возможно имеет смысл все загруженные файлы хранить как Attachment или MediaFile (надо продумать) и как-то помечать что это — версия, референс, ревью от продюсера или что-то другое.

Возможно статусы можно заменить на **Стикеры** — отдельную настраиваемую сущность с состояниями, которая может быть привязана к кадру или задаче.

Т.е. создаем стикер "Статус кадра", у которого список состояний равен списку статусов выше. Или например стикер "Приоритет", где список состояний — "Высокий", "Нормальный", "Низкий".

Стикеры требуют тщательного обдумывания.

## Какие функции должны быть в MVP

### Права доступа

Цель — иметь возможность управлять доступом на уровне отдельных объектов.

Один пользователь — один аккаунт в системе. Пользователь может состоять в нескольких компаниях и проектах с разными ролями. Один и тот же человек может быть координатором на одном проекте и рядовым исполнителем на другом. Права можно назначать как на пользователя, так и на команду.

Роли контекстные и двухуровневые:

- **CompanyMembership** — роль пользователя в компании (используется как дефолт для всех проектов).
- **ProjectMembership** — опциональное переопределение роли на уровне конкретного проекта.

Если роль на уровне проекта не задана явно — наследуется из компании.

Роли настраиваемые. Начальный набор:

| Роль            | Права                                                               |
| --------------- | ------------------------------------------------------------------- |
| **Админ**       | Неограниченный доступ к любым объектам                              |
| **Продюсер**    | Полный доступ к компании                                            |
| **Координатор** | Полный доступ к проекту                                             |
| **Исполнитель** | Ограниченный доступ к проекту: не может создавать/изменять кадры    |
| **Фрилансер**   | Доступ только к кадрам, где есть назначенные на него задачи         |
| **Клиент**      | Только просмотр отдельных версий и возможность оставить комментарий |

Роли и права надо обсудить дополнительно.

### Пакетная загрузка

Любые объекты (пользователей, проекты, кадры, версии и пр.) можно создавать не только по одному, но и пакетом — загрузить Excel-файл или заполнить таблицу прямо на веб-странице. Так же работает и с файлами — закинули пачку версий и продолжили работать, загрузка и конвертация идёт в фоне.

Процесс сопоставления версий (да и вообще файлов) с кадрами надо продумать отдельно.

### Гибкие статусы

Настраиваемые наборы статусов для кадров и задач — под пайплайн конкретной студии, а не жёстко заданные разработчиком.

Для начала такой список статусов для шота:

- Не начат
- В работе
- Готов
- Есть комментарий
- Принят
- Отдан
- На паузе
- Отмена

Для каждой задачи внутри шота:

- Не начата
- В работе
- Готово

_На будущее:_ Нужна возможность создавать шаблон проекта, где по мимо прочего можно указать удобные статусы для конкретной студии и в каждом новом проекте использовать их. Идея требует дополнительной проработки.

### Лог проекта

История **всех** изменений по проекту — создание/изменение кадров, задач, изменение статусов, назначение исполнителей, загрузка файлов — всех событий без исключения: кто, что и когда сделал. Часть этих данных будет отображаться в Ленте событий.

Для измененных данных хочется видеть дифф было/стало как в гите.

### Чаты по кадрам и задачам

Минимальный набор функций:

- Ответы на сообщения
- Пересылка сообщений
- Редактирование собставленных сообщений. Время редактирования, например 10 минут, задается в настройках. Продюсер или координдинатор может редактировать любые сообщения.
- Реакции
- Упоминания (пользователей, кадров, задач)
- Прикрепление файлов к сообщениям
- Поддержка Markdown

Сообщения должны разделяться на пользовательские и системные — например "Костя загрузил версию PRJ_0060_v01" или "Рома назначен исполнителем на задачу ...".

Фича: При вставке или наборе уникального идентификатора объекта (кадра, задачи, версии и других) автоматически подставляется ссылка на объект. Систему уникальных идентификаторов надо продумать.

### Уведомления

#### Лента событий проекта

Пример:

8 июля

- **18:03** Василий добавил задачу _"Клинап тросов"_ на 7 кадров:
  - PRJ_0320
  - PRJ_0330
  - PRJ_0340
  - _Показать все_

- **18:01** Василий создал задачу: _Клинап тросов_
- **13:06** Коля загрузил версию PRJ_0060_v01:
  - [превью]

- **11:08** Вы написали в чате PRJ_0100: Полная красота! Мне нравится

7 июля

- **16:00** Коля загрузил версию PRJ_0100_v03:
  - [превью]
- **13:17** Вы написали в чате PRJ_0380: Вот тут, видимо, надо сгладить
  - [превью] [превью]
- **13:15** Вы написали в чате PRJ_0100: Здесь надо выдать исходник, пропустили

#### Уведомления на почту

Присылаем раз в 4 чата список событий за прошедшее время. В настройках можно задать интервал.

Надо обдумать где хранить подобные настройки. Это должны быть настройки проекта или настройки пользователя?

#### Всплывающие уведомления в интерфейсе

Присылаем, если пользователь находится в системе. В настройках можно задать срочность (важные уведомления присылаем сразу) и интервал.

#### Push-уведомления от браузера

Присылаем, когда пользователь офлайн. В настройках можно задать срочность (важные уведомления присылаем сразу) и интервал.

#### Уведомления в мессенджер

Опциональная интеграция с различными мессенджерами.

### Просмотр файлов

- Панорамирование и масштабирование изображения или видео
- Рисование по кадру/изображению
- Покадровый просмотр
- Сравнение (для версий) было/стало

В целом, хочется чтобы просмотрщик открывал все файлы — и вложения в чате, и референсы, и картинки с аннотациями, а не только версии.

### Конвертация файлов

Все загруженные файлы должны конвертироваться в облегченный вариант. Дополнительно создается превью — JPG небольшого размера.

- Видео — в 1920*1080 mp4
- Картинки — в оптимизированный JPG.

Настройки сжатия и размера файлов должны храниться в настройках проекта.

_На будущее:_ Настройки хранения исходного файла — удалить, оставить, отправить во внешнее хранилище.

Конвертирование файлов должно выполняться в фоне.

### Интерфейс

Отображение списка объектов (кадров, задач, версий):

- Два режима "таблица" и "карточки"
- Сортировка и фильтрация объетов

### Поиск

Быстрый поиск на Lunr.js и расширенный поиск по всем данным в БД.

### Настройки

Настройки компании, проекта и пользователя.

### Экспорт данных

Выгрузка данных в Excel.

### Доступ для клиентов

Просмотр версий по ссылке с паролем — клиенту не нужен аккаунт в системе.

_На будущее:_ можно отправить ссылку на одну версию, а можно выбрать несколько (например, за 3 дня) и отправить ссылку на них. На одной странице выводятся все выбранные версии. Идея требует дополнительной проработки.

### Метка «Хайрез»

- Когда пользователь в чате отправляет ссылку на хайрез, система пытается сопоставить ссылку с существующей версией (по имени файла или по контексту).
- Если сопоставление удалось — у версии устанавливается флаг `has_highres = True`.
- Такие версии визуально выделяются в списке (звёздочка, отдельный фильтр).
- Валидация URL — при отправке проверяется, что это корректный URL (или локальный путь)
